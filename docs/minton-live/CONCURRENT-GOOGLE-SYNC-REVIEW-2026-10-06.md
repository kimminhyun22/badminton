# 동시 기기 사용 요구 재검토 — 배포 보류

## 판정 정정

사용자가 원하는 것은 같은 Google 계정으로 여러 기기의 관리자 화면을 함께 사용하고, 명부·설정·대진·진행 변경을 양쪽에서 이어가는 것이다. debc831 후보는 **한 기기씩 이어받기만 구현**했다. 동시 관리자 사용은 미완료다. 150개 검사 및 브라우저14개 통과는 이 좁은 구현 범위의 근거일 뿐, 사용자 요구 전체 충족의 근거가 아니다.

현재 원격 적용 없음. 이번 재검토도 로컬 문서만 변경한다.

## 현재 코드의 정확한 동작

| 상황 | 실제 동작 |
|---|---|
| 같은 계정으로 두 번째 관리자 기기 열기 | `accountStart()`에서 다른 기기 임대 확인 후 안내 dialog를 띄우고 return. `boot()`/앱 스크립트 로드가 실행되지 않는다. 화면은 account-starting으로 숨겨져 있다. **비활성 관리자 기기에서 실시간 읽기도 안 된다.** |
| 실시간 화면을 별도로 보기 | 기존 일반 회원 링크는 로그인 없이 계속 동작하지만, 이는 두 번째 관리자 화면의 실시간 읽기를 구현한 것이 아니다. |
| 운영 넘기기 | 두 번째 기기가 ‘이 기기로 이어하기’를 누르면 request-transfer 저장. 기존 기기는 다음 tick에서 요청을 확인하고 편집 정지→진행 요청 최대5초 대기→계정 저장→release. 새 기기는3초 간격 확인 뒤 reload/acquire한다. 기존 기기는 안내 화면으로 돌아간다. |
| 기존 기기가 백그라운드/통신 단절 | 숨겨진 페이지는10초 tick을 건너뛴다. 임대45초 만료 후 새 기기가 마지막 **서버 저장본**으로 이어받을 수 있다. 원 기기의 미전송 변경까지 전달된다는 보장은 없다. 기존 사본과 충돌 화면으로 보호하는 방식이다. 인계 시간이 항상 즉시라는 보장도 없다. |
| 폰에서 코트 수, 태블릿에서 점수제를 동시에 수정 | 두 번째 관리자 UI가 열리지 않아 **동시 수정 자체를 차단**한다. 서로 다른 항목을 병합하지 않는다. |
| 오래된/오프라인 사본이 나중에 저장 | 서버는 활성 임대 소유 기기인지, 문서 전체 revision이 같은지 검사. 다르면 aborted. 기기는 사본을 보존하고 최신 계정 자료 선택을 요구한다. 다른 필드만 수정했어도 문서 revision 충돌이면 자동 병합하지 않는다. |
| 동일 요청 재시도 | 현재 마지막 저장 receipt에 대한 중복 방지. 여러 기기 명령이 교차하는 동시 편집용 영수증 보존 체계로는 부족하다. |

근거: `js/admin-workspace.js`의 accountStart/boot/tick/surrender, `functions/admin-workspace.js`의 change/acquire/save. 또한 `js/team.js:pushLiveState`는 live 상태 전체를 직접 update한다. 단순히 임대를 없애면 계정 캐시 CAS 밖에서 기존 경기 상태를 덮어쓸 수 있다. 브라우저 가드만으로 서버 도착 지연까지 해결했다고 볼 수 없다.

## 최소 추가 설계 — 아직 구현하지 않음

1. **모든 기기에서 관리자 UI와 읽기를 연다.** 전역 단일 편집 임대를 제거한다. 포커스된 입력과 미전송 변경을 유지하면서 서버 확정 상태를 반영한다. inactive 안내를 동시 조회 기능으로 간주하지 않는다.
2. **명부/준비 설정은 항목별 변경 명령으로 저장한다.** 예: member.update(memberId, field, expectedVersion, value), settings.patch(eventId, expectedFields, changes). 전체 localStorage JSON 업로드를 실시간 원본으로 사용하지 않는다. 현재 daily 설정·경기가 같은 JSON 문자열 키 안에 있으므로 localStorage ‘키별’ 비교만으로는 충분하지 않다.
3. **독립 변경은 모두 반영한다.** 서로 다른 회원/필드의 변경은 서버 트랜잭션에서 최신 원본에 재검증 후 적용한다. 같은 필드 또는 연관 제약(코트 수 축소와 해당 코트 경기 시작, 진행 선수 삭제와 게임 종료)은 무조건 자동 병합하지 않는다. 최신 값을 보여주고 충돌한 항목만 재확인한다. 마지막 저장자가 전체를 덮는 방식은 사용하지 않는다.
4. **경기 진행의 원본은 기존 서버 엔진으로 통일한다.** 종료·선수 교체·코트 변경·되돌리기를 경기ID/예상 선수 지문/operationId로 서버에서 직렬 처리한다. 같은 경기 두 번 종료는 효과1회, 다른 코트 동시 종료는 효과2회가 되어야 한다. 계정 백업의 경기 스냅샷으로 서버 진행을 복원/덮어쓰지 않는다. 특히 팀전 관리자 직접 update 경로를 계정 모드에서 명령 전송으로 바꾸고 서버 결과만 반영해야 한다.
5. **전송 대기함과 영수증을 여러 요청 단위로 보존한다.** 기기ID+operationId로 성공·실패 결과를 추적하고, 응답 유실/역순 응답/재접속에서도 같은 작업을 중복 적용하지 않는다. 현재 마지막 receipt 한 개 대신 명령별 기록과 명시적 보존 기간이 필요하다.
6. **권한은 계정과 세션 사이에서 서버가 확인한다.** 새 계정 세션은 해당 UID로 생성하고, 기존 비회원 세션은 사용자 명시 동의와 기존 운영 capability 검증을 모두 거쳐 연결한다. 링크ID/회원 이름/로컬 명부만으로 소유권을 부여하지 않는다. 계정 연결 레코드는 공개 live 필드가 아닌 비공개 서버 경로에 둔다.
7. **DB 규칙 동결을 유지하는 초기 경로**: 새 private 계정 설정은 인증 callable의 증분 조회(포그라운드 약3초 목표, 네트워크 지연 별도)로 받는다. 기존 공개 경기 결과 구독과 결합한다. 이는 즉시 push가 아니라 짧은 간격의 동기화다. 비공개 RTDB 직접 실시간 구독을 채택하려면 좁은 UID read 규칙 변경이 별도 필요하며, 현재 승인 범위에 넣거나 수정하지 않는다.

단순히 ‘읽기 전용 두 번째 화면’만 추가해도 동시 수정 요구는 여전히 미완료다. 위 변경 중1~7과 아래 검증을 통과해야 동시 사용 완료라고 보고할 수 있다. 소요 일정은 이 명령 전송 경로 분석·구현 전 확정하지 않는다.

### 완료를 판단할 추가 검증

- 두 관리자 화면을 동시에 열고 인계 버튼 없이 같은 최신 내용을 표시.
- 폰의 코트 설정과 태블릿의 독립 명부 수정이 모두 보존. 같은 필드 충돌 시 해당 항목만 중단.
- 명부 삭제/선수 교체/대진 생성의 교차 충돌, 대진 생성 중 참가자 변경을 재검증.
- 같은 경기 동시 종료1회, 서로 다른 코트 종료2회, 코트3개 유지, 선수 자동 대체 없음.
- 오프라인 대기 명령이 나중에 와도 새 결과를 덮거나 완료를 재실행하지 않음.
- 계정 전환 중 응답 도착, 로그아웃 뒤 재전송, UID B의 A 접근 거절, 회원 링크 비로그인 유지.
- 실제 Google·실기 iPad Safari/PWA·연결된 LIVE/팀전에서 같은 시나리오 확인. 현재 합성 검사와 따로 기록.

**현재 후보 배포 승인은 요청하지 않는다. 요구 차이를 먼저 보완해야 하며, 아래 후속안도 미구현·미승인이다.** 특히 앞 문서의 ‘새 함수1개만 배포’는 단일 기기 후보의 범위이며 동시 사용 완성본의 확정 배포 목록으로 재사용하면 안 된다.

| 롤백 | 승인 직전 운영 기준 commit/SW 및 함수별 배포 revision/Google 설정을 기록한다. 새 기능 서버 kill-switch를 먼저 끄고, 정적 변경은 forward revert와 새 SW 버전으로 되돌린다(강제 push 없음). 새 함수는 비활성화 후 필요하면 삭제, 기존 함수 변경분은 기록한 revision 코드로만 재배포. Google provider/domain을 기존 사용자 영향 없이 복구할 수 있는지 확인하고 자동으로 공급자를 끄지 않는다. 비회원 원본·계정 사본/서버 명령 기록을 보존하고 신자료를 구형 원본에 자동 복사하지 않는다. 임시 데이터는 시험에서 만든 정확한 UID/이벤트ID만 정리한다. |
